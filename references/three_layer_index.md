# 三层索引体系详解

> **版本**: v1.1
> **设计理念**: 多维度检索，覆盖人脑的三种查找路径
> **v1.1 升级（来源：insigoo-memory GDT 通用化）**: 第 3 层「提问场景索引」从朴素"问题→路径"表，升级为 **受治理查询场景索引**（GDT-Core 六要素 + 六约束治理），并新增「闲聊 vs GDT 触发」双模式反应模型。

---

## 为什么需要三层索引？

### 人脑的三种查找模式

想想你平时怎么找东西：

1. **按位置找**："那个文件在哪个文件夹？"
   - 你记得大概位置，需要确认路径

2. **按主题找**："关于零废弃分类，我们有什么资料？"
   - 你知道要找什么主题，但不知道具体文件

3. **按问题找**："我想知道怎么组织社区活动，去哪查？"
   - 你有一个问题，需要找到能解答的文档

**单层索引（只有目录）只能覆盖第1种**。三层索引覆盖全部三种。

### 传统索引的问题

传统知识库只有一个"目录"或"文件列表"：
- 只能按文件名/位置找
- 找不到"关于某主题的所有资料"
- 新人不知道"想了解XX该看什么"

**三层索引**解决这三个问题。

## 三层结构详解

### 第1层：目录索引（按文件位置）

**回答的问题**："XX文件在哪？"

**格式**：表格，列出所有文件的位置和简要说明

```markdown
## 第1层：目录索引

| 类别 | 位置 | 关键内容 |
|------|------|----------|
| 组织简介 | org/intro.md | 使命、愿景、业务范围 |
| 项目A | projects/项目A/ | 项目A相关文档 |
| 会议纪要 | org/meetings/ | 各类会议记录 |
```

**维护规则**：
- 新增文件 → 在对应类别添加一行
- 删除文件 → 移除对应行
- 每周检查：是否有文件未被索引（孤立文件）

### 第2层：主题索引（按知识实体）

**回答的问题**："关于XX主题有什么资料？"

**格式**：每个主题一个小节，提炼关键信息

```markdown
## 第2层：主题索引

### 零废弃分类标准

- **定义**：按材质分类可回收物（塑料/金属/纸/玻璃/电子）
- **标准来源**：国家标准GB/T XXXX
- **本地适配**：增加社区常见品类
- **关键文件**：
  - methods/零废弃分类方法.md
  - cases/2026-06-20_分类实践.md

### 社区动员方法

- **核心策略**：意见领袖+激励+示范
- **适用场景**：环保/健康/安全类社区活动
- **关键文件**：methods/社区动员方法.md
```

**维护规则**：
- 新增重要主题 → 添加主题小节
- 主题信息有变 → 更新关键信息
- 每月审核：主题信息是否过时

**价值**：不需要打开文件就能快速复习关键知识。

### 第3层：受治理查询场景索引（GDT-KB 六要素 + 六约束）

> v1.1 升级：第 3 层不再是朴素"问题→路径"表，而是**受治理知识查询任务**——每个高频查询场景是一份契约，按 **GDT-Core 六要素**组织、受 **GDT-Core 六约束**守护（详见 `insigoo-memory` 技能与 `GDT通用化升级与知识库索引治理方案.md`）。

**回答的问题**："我想知道XX，去哪找 / 怎么查得准？"

**两种入口（双模式，见 3.1）**：闲聊/自由查询（灵活） vs GDT 触发查询（受治理）。

**格式**：每个场景条目 = 一份受治理查询契约（yaml）：

```yaml
- scenario_id: kb.disclosure.project-full   # 命名：kb.<领域>.<动作>
  display_name: 项目全周期披露文档检索
  question_examples:                        # 要素① 查询提示词（触发语≥3条）
    - "某项目的全部披露文档在哪"
    - "把 X 项目的立项到结项材料都找出来"
  source_scope:                             # 要素② 数据源（受治理语料，锁定）
    - proposal
    - implementation
    - monitoring
    - evaluation
    - finance
  mapping_table:                            # 要素③ 知识库/映射表（问题→文档节点，版本化）
    - 项目立项文件 → proposal/<项目>/建议书.md
    - 结项评估 → evaluation/<项目>/终期评估.md
  query_spec:                               # 要素④ 查询规范（检索口径，固化）
    retrieve_within: source_scope
    must_cite: true                         # 约束③ 事实引用必带出处
  compute_and_report:                       # 要素⑤ 计算规范+报告框架
    method: SAG 语义检索 + 编译
    report_framework: 知识卡片（标题/出处/摘要/关联）
  output_format:                            # 要素⑥ 输出格式
    - 引用文档原文
    - 知识卡片（带出处）
    - AI 解读.md（独立，标"AI 分析"）
  open_params:                              # 用户运行期可填项
    - 项目名
    - 年份
  locked_contract:                          # 约束② 锁定契约（运行期不可改）
    label_synthesis: "AI 分析"
    version: v1.0.0                         # 约束④ 版本不可覆盖
  fallback: BLOCKED                         # 约束⑤ 无命中不编造
  status: PUBLISHED
```

**维护规则**：
- 发现高频问题 → 添加场景条目（按上 schema 写契约，而非一行映射）
- 新人常问的问题 → 优先添加
- 每季度审核：场景是否仍有效、`version` 是否需升版

**价值**：新人/外部人员秒级定位；更重要的是——AI 检索时**不再越界、编造、静默漂移**，知识库从"文件夹"升级为"受治理查询生产系统"。

#### 3.1 双模式反应模型：闲聊 vs GDT 触发

> 现实：很多组织的查询是自由、灵活的，并非每个问题都该被契约管死。第 3 层必须分清两种入口，agent 反应规则不同。

**判定层（Trigger Decision）**：
1. 提取用户意图与关键词；
2. 与已发布 scenario 的 `question_examples` 做语义匹配；
3. 命中 → **GDT 触发模式**；否则 → **闲聊/自由查询模式**；
4. 闲聊中若检测到「对外披露/合规/敏感数据/需审计」信号 → 主动提示升级到 GDT 触发模式。

| 维度 | 闲聊 / 自由查询模式 | GDT 触发模式（受治理） |
|------|-------------------|----------------------|
| 是否加载 `locked_contract` | 否 | **是** |
| 检索范围 | SAG 全量（灵活） | 仅 `source_scope` 受治理语料 |
| 引用要求 | 优先基于事实，不强制 | **必带出处**（`must_cite`） |
| AI 解读 | 自由综合，可标可不标 | 独立标注「AI 分析」 |
| 无命中 | 灵活回应 / 建议补充 | `fallback: BLOCKED`，不编造 |
| 产物性质 | 非正式、不索引、不审计 | 正式受治理产物 |
| 对外披露 | 不得当作正式资产 | 合规、可审计 |

> 两者共用 SAG 检索引擎，差异只在"是否加载 `locked_contract`"。

## 如何建立三层索引？

### 从零开始（5步）

1. **盘点现有文档**
   - 列出所有 `.md` 文件
   - 标注每个文件的主题和类型

2. **建立第1层（目录索引）**
   - 按目录结构分类
   - 每个文件一行：位置 + 简要说明

3. **建立第2层（主题索引）**
   - 提取所有文档的关键主题
   - 每个主题提炼3-5条关键信息
   - 标注关键文件路径

4. **建立第3层（受治理查询场景索引）**
   - 想象新人/外部人员会问什么高频问题
   - 每个场景按"受治理查询契约"schema 写（要素：查询提示词/数据源/映射表/查询规范/计算报告/输出格式）
   - 优先覆盖高频 + 涉及披露/合规的场景（这些最该受治理）

5. **验证**
   - 让不熟悉的人试用索引找东西
   - 根据反馈调整

### 使用模板

参考 `templates/knowledge_index.md`，包含完整的三层索引模板，可直接复制修改。

## 索引维护规则

### 核心原则

1. **写入即索引** —— 新增文档必须同步更新索引
2. **不存废弃** —— 过时文档移入 `archive/`，索引中标注"已归档"
3. **定期审计** —— 每周检查孤立文件，每月审核主题信息

### 更新触发条件

| 事件 | 更新哪层 | 更新内容 |
|------|---------|---------|
| 新增文件 | 第1层 | 添加文件条目 |
| 新增重要主题 | 第2层 | 添加主题小节 |
| 发现高频问题 | 第3层 | 添加提问场景 |
| 文件内容大改 | 第1+2层 | 更新说明和主题信息 |
| 文件删除/归档 | 第1层 | 移除或标注归档 |

### 维护节奏

| 频率 | 动作 | 耗时 |
|------|------|------|
| 随时 | 新增/修改文档后更新索引 | 2分钟 |
| 每周 | 检查孤立文件 | 10分钟 |
| 每月 | 审核主题信息是否过时 | 30分钟 |
| 每季度 | 全面重建索引，优化结构 | 1小时 |

## 索引质量检查清单

```
□ 第1层覆盖所有文件？（无孤立文件）
□ 第2层覆盖所有重要主题？
□ 第3层覆盖高频问题？
□ 第3层高频场景是否已写成"受治理查询契约"（含 source_scope / locked_contract / fallback）？
□ 索引中的路径都有效？（无断链）
□ 主题信息是最新的？
□ 提问场景覆盖新人的常见问题？
```

## 与RAG的关系

三层索引和RAG是**互补**关系：

| 维度 | 三层索引 | RAG |
|------|---------|-----|
| 检索方式 | 人工查表 | AI自动检索 |
| 精确度 | 高（人工标注） | 中（语义匹配） |
| 维护成本 | 高（需手动更新） | 低（脚本自动） |
| 覆盖范围 | 核心知识 | 全部文档 |
| 适用场景 | 已知要找什么 | 模糊查询 |

**最佳实践**：
- 文档<20篇：只用三层索引
- 文档20-200篇：三层索引 + RAG
- 文档>200篇：三层索引 + RAG（必须）

三层索引帮助**人**快速定位，RAG帮助**AI**自动检索。两者结合，知识库才能真正好用。

**v1.1 补充 · GDT 触发模式下的 RAG**：当第 3 层命中 GDT 触发场景，RAG 检索被 `source_scope` + `locked_contract` 约束——只检索受治理语料、必带出处、无命中即 BLOCKED；闲聊/自由查询则走"灵活 RAG"，不被契约管束。同一套 SAG，两种治理强度。

## 示例：一个完整的三层索引片段

```markdown
# 知识库索引

## 第1层：目录索引

| 类别 | 位置 | 关键内容 |
|------|------|----------|
| 组织简介 | org/intro.md | 零废弃倡导组织，成立于2020年 |
| 社区项目 | projects/社区回收/ | 社区可回收物回收项目 |
| 分类标准 | methods/分类标准.md | 五大类可回收物分类方法 |

## 第2层：主题索引

### 零废弃分类

- **五大类**：塑料、金属、纸、玻璃、电子
- **标准**：国标GB/T XXXX + 社区适配
- **关键文件**：methods/分类标准.md

### 社区回收项目

- **状态**：进行中（2026年3月启动）
- **覆盖**：5个社区，月回收2吨
- **关键文件**：projects/社区回收/进展.md

## 第3层：受治理查询场景索引

```yaml
- scenario_id: kb.org.intro
  display_name: 组织介绍检索
  question_examples:
    - "我们组织做什么的"
    - "分类标准是什么"
  source_scope: [org/intro.md, methods/分类标准.md]
  mapping_table:
    - 组织简介 → org/intro.md
    - 分类标准 → methods/分类标准.md
  query_spec:
    retrieve_within: source_scope
    must_cite: true
  compute_and_report:
    method: SAG 语义检索
    report_framework: 知识卡片（标题/出处/摘要）
  output_format: [引用原文, 知识卡片]
  open_params: []
  locked_contract:
    label_synthesis: "AI 分析"
    version: v1.0.0
  fallback: BLOCKED
  status: PUBLISHED
```

> 注：这是"小组织"简化样例。高频/披露/合规场景须按上方完整 schema（六要素+六约束）写契约。完整可运行**示范任务包集**归档于 `references/gdt_kb_samples/`（共 15 个 `gdt_kb_sample_*.md` + `README.md` 索引表，含场景/红线/敏感度分级），详见 `references/gdt_kb_samples/README.md`。
